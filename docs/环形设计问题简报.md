# 时间追踪产品 · 圆环设计问题简报

> 用途：给外部产品经理／设计师看的自包含简报。
> 包含：产品定义 → 当前形态 → 问题 → 已否掉的方案 → 待定的问题。
> 最后更新：2026-10-12

---

## 一、产品是什么（我的定义，这部分是前提，不是要讨论的）

### 1. 24 小时不间断记录，**没有「停止」**

时间永远不会停止，所以：

- **不存在"空档"** —— 每一个时刻都归属于某个分类
- 产品的终局是**24h 全时段都有标签**
- **切换分类才是主路径**；「停止/暂停」只是当前多端能力还不齐（win / mac / 安卓 / iOS / watch 未能全部操作）时的**临时妥协**
- 推论：任何依赖"空档"来表达的可视化（比如"几点在做什么"的时间轴）**在本产品里是没有意义的** —— 因为没有空档，时间轴退化成"换个顺序的构成图"

### 2. 记录必须**无感**

用户不应该为了"记录"这件事做任何操作。产品要**简单再简单**。
任何增加理解成本的视觉元素，都与产品定义冲突。

### 3. 数据的去向

结构化日志 → Google Doc → NotebookLM，用于回顾个人每日状态。

## 二、当前形态（已经做出来的）

### 三端 + 一个云端

| 端 | 说明 |
|---|---|
| **桌面悬浮组件** | Electron，常驻桌面、透明窗口、置顶、无边框 |
| **网页版** | 与组件同一个站点；`?widget=1` 即组件形态，`?widget=1&sandbox=1` 为本地预览 |
| **微信小程序** | 手机端 |
| **云端** | 空间模型：设备令牌 + 6 位配对码，**免登录**；三端共用同一份数据 |

（组件加载线上网址，**界面改动热更新，不用重打 exe**；只有 Electron 外壳改动才需要重打包）

### 桌面组件的交互（已定型，本轮不改）

```
常驻：圆形玻璃表盘 + 环心读数（当前分类名 + 实时用时，格式只有分秒）
         ↓ 滚轮一滚
浮层：方形柔边遮罩盖住表盘（背景模糊）
      荧光条列表（循环滚动，条长 = 今日时长，文字嵌在条内）
      末位固定「＋ 新增项目」（不进滚轮序列，只接受点击）
         ↓ 停住 900ms 或点击
结果：切换到该分类 —— **只切换，绝不停表**
      正在计时的那一段：色块呼吸高亮
```

### 视觉基调

- **Raycast**：表面阶梯 + 1px 发丝描边 + 不用投影做层级
- **Apple HIG**：圆头进度弧 + 大号数字 + 等宽数字（tabular nums）
- 组件窗口约 260×380，表盘直径 152px

## 三、问题（要请教的核心）

### 现在的圆环怎么画的

```
弧长 = (360° − 幽灵槽) × 该分类今日秒数 ÷ 今日总和
其中「今日秒数」已经包含「正在计时那一段」的实时秒数
```

**分母是「今日总和」—— 也就是"今天所有有记录的分类加起来的时长"，不含任何固定参照。**

### 两个后果（我实际感受到的）

1. **今天刚开始一个计时，这个分区就一下子填满整个圆环**（哪怕只过了 1 秒）
   —— 而且它是从"灰色幽灵"一秒跃成"唯一有记录项"，视觉上是**跳变**
2. **记录满 24h 之后，早上打开看到的就是 8h 睡眠占满整个圆环**

### 我的总结（我认为这是问题的本质）

> **"符合了数据的逻辑，不符合人类的逻辑。应该让数据服务人，而不是人服务数据。"**

更深一层：**圆环天生被读作"完成度"**（因为 Apple 活动圆环就是这个语义），
但**我们没有任何"完成"的定义** —— 不设目标、不设配额，那"满"到底意味着什么？
我怀疑"用环不合适"的根源在这里。

## 四、已经试过并被否掉的方向（避免重复劳动）

| # | 方向 | 否掉的理由 |
|---|---|---|
| 1 | 保持现状，只给非零项加最小弧长 | 治标；"今天只有一条 → 占满整圈"依旧 |
| 2 | 分母改成 **24 小时占比** | 仍不满足"人类的逻辑" |
| 3 | 分母改成 **已过的时间**（0点→现在） | 早上睡眠仍会占掉约 3/4 圈 |
| 4 | **24 小时时间轴环**（位置=几点发生） | **本产品没有空档**（时间永远在走）→ 时间轴退化，无价值 |
| 5 | 分类**强度环**（不比长度，比浓淡） | 看不出"工作比学习多多少" |
| 6 | **双环**（外圈时间轴 + 内圈占比） | **两个环对多端交互是障碍** |
| 7 | 环**只画今天这一段**（极简环） | 被认为不是想要的 |
| 8 | **饼图式**（永远铺满、分母24h、未记录占中性一格） | 被认为不是想要的 |

## 五、想请教的问题

### Q1｜环是「讲构成」还是「讲程度」？★ 最关键
- **讲构成** = 环是一张饼：今天由哪些事组成
- **讲程度** = 环是一个进度：今天走到哪了 / 记录了多少
- 这一条决定后面所有细节（我上面 8 个方案来回摇摆，根源就是它没定）

### Q2｜「构成」这件事，切换列表已经讲了，环还要不要再讲一遍？
（悬浮列表本身就是"按今日时长排序的荧光条"）
- 要 → 环是饼图（信息冗余，但有一眼感）
- 不要 → 环只回答"今天走到哪了"，构成交给列表（更简，更贴合"无感"）

### Q3｜环上要不要出现「没记录」这件事？
- 出现（中性灰一格）→ 它会自然长成"24h 覆盖率"读数（原本就规划过的扩展点，不用额外做 UI）
- 不出现 → 环上永远只有彩色，看不到"漏了多少"

### Q4｜「刚开始计时」那一瞬间，应该看到什么？（这是最初的触发点）
- 一颗小药丸，随时间慢慢长大
- 什么都不变（只在跨过某个阈值时才动）
- 从环心"漫"出来

### Q5｜「正在计时」怎么表达？
（现状：那一段呼吸闪烁 + 环心大数字）
- 保留呼吸
- 换别的：外圈一道细环 / 环心跳动 / 整圈微微提亮

## 六、技术约束（供参考）

- 三端（桌面组件 / 网页 / 小程序）**共用同一套环形几何**，改动要同步；
  项目里有一份 `prototype/ring-geometry.js` 作为奇偶校验参考实现
- 桌面组件上表盘直径 **152px**，圆周长约 339px → **1° ≈ 0.94px**；
  小程序上环更大（1° ≈ 1.5px），所以"最小可见角度"这类常量**不能跨端共用同一个值**，要按周长归一
- 现在的弧用**圆头线帽**（round linecap）—— 这是"进度条"的视觉语言
- 环**不再兼做启动器**（切换已经交给悬浮列表），所以不必再保留"未开始分类"的点击入口和幽灵药丸
